# GB10 native dependency map (issue #286, cut A)

Status: source inventory. No builds, no tests, no hardware runs, no GPU access were done to write this. Every row was read from source at the pinned commits below. Claims are tagged OBSERVED (read in source), INFERRED (with confidence) or UNKNOWN.

## Plain-English summary

Today the GPU works on this machine because a Linux program talks to NVIDIA's Linux driver through special device files. Omega's code never touches the chip directly. Everything it does goes through two small layers in the PHYSICS repo, which in turn ask the NVIDIA driver to do the hard work (wake the chip, load firmware, build memory maps, create a work queue, report faults).

For AIENOS to run the GPU without Linux, three things have to be true:

1. The part of Omega that makes GPU programs (instruction encoding, work descriptors, constant banks) must keep working. It is mostly plain C with no Linux dependency, so it can be reused. OBSERVED.
2. Everything the Linux driver does for us today must be done by AIENOS code instead. That is the long list in section 3. Nothing in the current code does any of it by itself. OBSERVED.
3. The pieces of Omega that are tangled up with Linux (a global lock, clocks, memory allocation, sleeping, threads) need a small "platform services" layer so the same code can run on both. OBSERVED that the tangle exists, INFERRED (medium) that a services layer is the right fix.

The vector engine (`OmegaGpuBackend`) is already a clean seam. The persistent session, the numerical launchers, the resident runtime and the accelerator world are not: they call the driver layer directly. Section 5 says which cut moves each one. Section 6 says what waits on the open execution-order decision and which steps only Drake can do (boots, firmware, chip use under AIENOS).

## 7. Order dependencies

Sources: `CURRENT_EXECUTION_PLAN.md` line 720 and NEXT-PHASE-3 (lines 791 to 800) in aien-architecture; issue #286 text; issue #285.

Two orders exist for native AIENOS. Order 1 (older): M5 trust, M6 network, M7 inference, M8 persistent agent. Order 2 (NEXT-PHASE-3, newer): operator input, boot selection and rollback, PCI discovery, real-device storage, owner identity and trust, native inference, then GPU later. Both place GPU after native CPU inference (OBSERVED in the plan; the plan states Campaign 3 lists "later GPU"). The plan recommends Order 2 but records that Drake decides.

### Can proceed now (host-only, no physical device, no kernel-order commitment)

- Cut A in full: this map, the platform-services contract, hiding `NvrmMem` behind typed handles, moving `nvrm_mthd` and `nvrm_gp_entry` into a shared encoding header, a freestanding link target for the codegen, QMD and engine files, backend contract tests over the existing fake. INFERRED (high): no kernel or hardware change.
- B host fixtures: multi-segment MCFG parsing tests, fake config-space access that fails on any write, GPU identity fixture on a nonzero segment, malformed and overlapping entry tests. These are pure parsing and fixtures. The issue already authorizes "Host-only interface, parser, fixture, and refusal work".
- C host work: inventory of firmware and protocol sources, parsers and refusal tests for firmware metadata. No loading.
- D host work: simulated-device tests for allocator, address-space bookkeeping and refusal paths, using no real GPU.

### Cannot start until #163's decision is made, or needs coordination first

These items change shared kernel code or occupy a place in the native sequence, so scheduling them depends on which order governs. INFERRED (medium); the plan does not list per-step dependencies, so this is my reading.

| Cut and step | Why it waits |
| --- | --- |
| B: wiring multi-segment discovery into the boot path, or changing `pci_enumerate` / `pci_stage_probe` | Order 2 puts PCI discovery right after boot selection; Order 1 does not schedule PCI before M7. The first PR (aienos#287) only adds new read-only functions and host tests and leaves the boot path unchanged; the coordinator confirmed on 2026-10-08 that no other lane owns `pci.c`. |
| B: capability-bound MMIO, DMA and interrupt resources in the kernel | Touches IPC/capability code and `ck_mmio_map`, which trust and physical-memory-authority work also rely on. Order matters for what exists first. |
| B: IORT/SMMU audit and extension for a second SMMU, GIC/ITS work for an interrupt route | Same shared kernel areas; storage and input lanes use them. |
| B: QEMU gates for the above | Gate numbering and CI are shared. |
| C: all implementation beyond host parsers | Requires physical bring-up prerequisites (see below). |
| D: any kernel-side allocator or queue code merged to main | Depends on the B resources and on #285 when it reuses domain-1 numbers. |
| E: all | Follows first compute. |

- OPERATOR STEP: any firmware load or GSP handoff on real hardware.

Per the issue, these also wait on: native input and recovery, boot rollback, physical memory authority, and the relevant storage and trust dependencies. INFERRED (high) that the physical GB10 DMA/translation question (is the GPU behind the SMMU window?) must be answered before C or D can run with confinement.

### Issue #285 trigger

OBSERVED in #285: the first change that lets a domain-1 kernel resource number (kind 2 or 3: kernel channel or object) be destroyed and reissued at run time, or persists one across reboot or rollback, must implement the per-resource incarnation counter in the same change. Until then `gen_lookup` has no real counter and nonzero `required_generation` is refused.

Where it may bite here. A GPU channel is the likely domain-1 kernel channel (INFERRED, medium) and cut D must "destroy and reopen" it (issue acceptance: normal teardown/reopen, repeated runs). If the native channel is released and its number reissued, the counter must ship in that cut. If cut D keeps one channel number per boot and never reuses it, the trigger does not fire. UNKNOWN: which GPU-private allocations map to domain 1 (the issue says to define this mapping explicitly; no such mapping exists in the files read here). The counter must not be equated with handle-slot generations or Omega world epochs (#285 text).
